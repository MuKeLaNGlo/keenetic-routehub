# Политика сети и устройств

RouteHub связывает устройства с политиками по MAC и подтверждённому адресу IPv4. Проверка маршрута показывает расчётное правило и результаты отдельных сетевых проб.

## Приоритеты RouteHub

| Режим | Порядок |
| --- | --- |
| Устройство без отдельной политики | Глобальные правила сверху вниз, затем глобальный маршрут по умолчанию. |
| `inherit` | Условия устройства сверху вниз, затем глобальные условия и глобальный маршрут по умолчанию. |
| `override` | Условия устройства сверху вниз, затем явно заданный маршрут устройства по умолчанию. |

Первое совпадение завершает выбор. Пустой глобальный `defaultTarget` означает `direct` и сохраняет поведение ранних конфигураций. Новое устройство наследует глобальные настройки при подключении к охваченному сегменту. Применённую политику устройства можно увидеть в объяснении маршрута по полям `scope` и `deviceMAC`. Домен по умолчанию включает поддомены. Поле `exact: true` ограничивает совпадение самим доменом и компилируется как `full:`.

```json
{
  "defaultTarget": "direct",
  "rules": [
    {"name": "Видео", "domain": "video.example", "target": "vpn"}
  ],
  "devices": [
    {
      "mac": "02:00:00:00:00:20",
      "label": "Ноутбук",
      "addresses": ["192.168.50.20"],
      "mode": "inherit",
      "rules": [
        {"name": "Видео на ноутбуке", "domain": "video.example", "target": "direct"}
      ]
    },
    {
      "mac": "02:00:00:00:00:21",
      "label": "Тестовое устройство",
      "addresses": ["192.168.50.21"],
      "mode": "override",
      "defaultTarget": "vpn"
    }
  ]
}
```

Здесь `vpn` обозначает ID существующего профиля. Условия без совпадения для ноутбука идут по общей политике. У тестового устройства весь оставшийся трафик идёт через `vpn`.

## Интеграция

- `devicepolicy.Compile(config, options)` проверяет правила и фиксирует порядок. `Options.Targets` сопоставляет ID VPN-профилей с протоколами. Теги `direct` и `zapret` встроены. `Options.LAN` содержит настроенный IPv4 CIDR перехвата, `Options.RouterIP` исключает шлюз из адресов устройств.
- `Plan.XrayRules("lan-transparent")` выдаёт готовые правила `routing.rules` для `domainStrategy: "AsIs"`. У персональных правил есть `sourceIP` `/32` и `inboundTag`. Локальный SOCKS получает глобальные правила. Для запуска без прозрачного перехвата передайте пустой `inboundTag` и соберите план без `Options.LAN`, если диагностика должна показывать состояние этого запуска. [Условия маршрута Xray](https://xtls.github.io/en/config/routing.html).
- `Plan.Evaluate(destination)` принимает домен или IP назначения, `tcp`/`udp` и порт. `ClientMAC` или `ClientIP` выбирают область диагностики. Когда известны одновременно домен из TLS/QUIC и IP назначения, передайте IP в `targetIP`, чтобы учесть совпадения CIDR наравне с доменами. Вывод описывает выбор правила. Доступность сервера надо проверять отдельной пробой. [Контекст маршрутизации Xray](https://github.com/XTLS/Xray-core/blob/0afec660/features/routing/session/context.go).
- `Plan.Devices()` возвращает канонический MAC, подпись, адреса, режим, `active` и код причины для неактивного устройства. `lan-disabled` означает отсутствие IPv4-перехвата, `missing-address` — отсутствие указанных адресов, `unverified-address` — несовпадение или конфликт в переданном инвентаре.

## Привязка адресов

Записывайте IPv4 устройства после назначения ему постоянного DHCP-адреса в Keenetic. Для Wi‑Fi используйте стабильный MAC именно для этой сети. Модуль проверяет формат MAC, дубли, границы подсети, адрес сети, шлюз и broadcast. IPv6 сейчас остаётся вне персональных правил, пока сам перехват поддерживает только IPv4. [Список клиентов Keenetic](https://support.keenetic.com/hopper/kn-3811/en/14007-client-lists.html), [регистрация устройств](https://support.keenetic.com/hopper/kn-3811/en/14008-connected-devices-registration.html).

Без инвентаря компилятор использует постоянные привязки, заявленные администратором. При переданном `Options.Inventory` каждый адрес должен иметь ровно одного владельца в снимке и совпадающее подтверждение `Fixed`. Запись из ARP, таблицы соседей или динамической аренды может выявить конфликт, но сама не подтверждает постоянную привязку. Пустой подтверждённый снимок деактивирует персональные правила. При этом действует глобальная политика.

`ReadKeeneticInventory(ctx)` читает локальный список клиентов через `/bin/ndmc -c 'show ip hotspot'`, настройки DHCP через `show running-config | grep "^ip dhcp host "` и таблицу аренд через `show ip dhcp bindings`. Фильтр выполняется внутри KeeneticOS. Для подтверждения постоянного адреса запись `ip dhcp host <MAC> <IPv4>` должна совпасть с записью того же MAC и IPv4 в таблице DHCP со сроком `infinity`. Это учитывает случай, когда настройка содержит IP вне действующих пулов. Адаптер дополняет сведения наблюдениями `/proc/net/arp`. Эти наблюдения могут выявить конфликт, а постоянный адрес подтверждается только данными двух команд DHCP. Адаптер работает с локальным CLI прошивки и не требует отдельной аутентификации из приложения. [Фиксированный IP клиента](https://support.keenetic.com/hopper/kn-3811/en/14008-connected-devices-registration.html), [справочник CLI KeeneticOS 5.1](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.1/en/cli_manual_kn-1812.pdf).

Перед компиляцией берите свежий снимок. В случае ошибки чтения передавайте пустой ненулевой `Options.Inventory`. Пока действует предыдущая конфигурация Xray, изменение DHCP-привязки требует повторной проверки и применения правил. Защита от подмены IPv4 требует отдельной проверки MAC на уровне LAN.

## Проверка

`go test -race ./devicepolicy` проверяет порядок правил, режимы, валидацию, конфликты адресов и разбор инвентаря. На KN‑3811 проверен формат команд чтения и совпадение 20 постоянных настроек с таблицей аренд. Дополнительно на Xray `26.10.29` в изолированном Linux ARM64 выполнены шесть локальных TCP-запросов через SOCKS с разными источниками. Подтверждены персональное правило, точное совпадение домена, наследование, полное переопределение, глобальная политика нового адреса и изоляция правил устройства от локального SOCKS. Фактический перехват после развёртывания требуется проверить с устройством в LAN.
