# DNS для клиентов Keenetic

При явном включении перенаправления RouteHub создаёт цепочку `RH_DNS_LAN` в таблице IPv4 NAT. Два входных правила подходят только клиентам заданного LAN-интерфейса и подсети, которые обращаются к IPv4-адресу роутера на порту 53 по TCP или UDP. Адрес назначения остаётся адресом роутера, меняется порт на порт резолвера RouteHub. DHCP, штатная DNS-конфигурация Keenetic, обращения к другим DNS-адресам и IPv6 остаются вне области этой цепочки.

Перед добавлением правил помощник проверяет IP интерфейса и принадлежность обоих сокетов процесса RouteHub. При закрытии сокетов или завершении процесса сторож удаляет собственные правила. NDM-хук восстанавливает цепочку после пересборки таблицы NAT, пока слушатель продолжает работать. Состояния команды `status` имеют значения `inactive`, `active` и `degraded`.

При наличии утилиты `conntrack` остановка удаляет записи с исходным назначением «адрес роутера, порт 53» и обратным источником «адрес роутера, порт резолвера RouteHub» для исходной подсети. Существующий UDP-сокет клиента сразу возвращается к штатному DNS. Без утилиты запросы с новым соединением сразу используют штатный DNS. Запись старого UDP-соединения действует до истечения времени в таблице conntrack. [Руководство conntrack](https://netfilter.org/projects/conntrack-tools/conntrack-manpage.html)

`test_lifecycle.py` предназначен для отдельного Linux-контейнера без доступа в WAN. Для проверки нужны `iptables`, `iproute2`, `unshare`, `nsenter`, `flock`, Python, IPv4 forwarding в сетевом пространстве контейнера и разрешения на создание изолированных сетевых пространств. Тест использует тестовые DNS-порты и проверяет реальное прохождение пакетов по двум транспортам, границы области, повторную установку правил и автоматическое восстановление штатного DNS. При наличии `conntrack` тест также проверяет возврат штатного DNS при следующем запросе с тем же UDP-сокетом.
